# Техническое задание на разработку системы контроля обучения по охране труда

## 1. Общие положения

### 1.1. Цель проекта
Создать десктопное приложение (PySide6) для учёта и контроля обучения сотрудников по охране труда в соответствии с Постановлением Правительства РФ № 2464. Приложение обеспечивает внесение данных о сотрудниках, прошедших обучение, формирование XML для передачи в реестр Минтруда (edu.rosmintrud.ru), хранение истории проверок знаний, формирование протоколов проверки знаний, а также сводный анализ статуса обучения сотрудников с возможностью запроса актуальных данных из реестра Минтруда.

### 1.2. Основные пользователи
Один пользователь с полным доступом ко всем данным и функциям приложения. Приложение не имеет встроенной системы авторизации — персональные данные защищены полевым шифрованием (Fernet + DPAPI).

### 1.3. Ограничения
- Работает на ОС Windows 10/11
- При наличии доступа к Интернету — интеграция с API Минтруда (edu.rosmintrud.ru)
- Обязательно наличие XSD-схемы в папке `schema/` для конвертации в XML
- Максимум 5000 записей в таблице workers_data
- Максимум 300 записей на один протокол (DOCX)

## 2. Функциональные требования

### 2.1. Вкладка «Внесение данных»

**Назначение:** Ввод данных УЦ и работодателя, загрузка данных сотрудников из Excel/XML, ручной ввод записей о прохождении обучения.

**Макет вкладки:** `QVBoxLayout` с `QScrollArea`, внутри три `QGroupBox`, расположенные вертикально.

1. **Группа «Данные УЦ и работодателя»** — `QGridLayout` (6 колонок):
   - ИНН УЦ + Название УЦ (строка 0)
   - ИНН Заказчика + Название Заказчика (строка 1)
   - Кнопка «Сохранить данные» (синяя, `_btn_style()`) (строка 2)

2. **Группа «Загрузка данных»** — `QFormLayout`:
   - Поле XSD-схемы + кнопка выбора (серая)
   - Поле файла + кнопка выбора + кнопка загрузки
   - Кнопки: «Создать шаблон» (серая), «Схема XSD» (серая)
   - `QProgressBar` (`progress_bar`)

3. **Группа «Ввод данных работника»** — описание + кнопка «Добавить работника вручную»:
   - Открывает модальный `QDialog` с полями (ФИО, СНИЛС, Должность, № программы + Справка, № протокола, Результат combo, Дата) и кнопками «Сохранить данные» / «Отмена»
   - `setObjectName` используется только на `showErrorsBtn`

**2.1.1. Данные УЦ и работодателя**
- ИНН УЦ (обязательное, 10 или 12 цифр)
- Наименование УЦ (обязательное)
- ИНН Заказчика (обязательное, 10 или 12 цифр)
- Наименование Заказчика (обязательное)
- Кнопка «Сохранить данные» — данные шифруются (AES/Fernet) и сохраняются в `data/org_settings.json`
- При загрузке Excel пустые поля ИНН/наименования автоматически заполняются из сохранённых настроек

**2.1.2. Загрузка данных**
- Поддерживаемые форматы: .xlsx, .xml (RegistrySet)
- Кнопка «Выбрать файл» — открывает диалог выбора файла (QFileDialog)
- Кнопка «Загрузить файл» — запускает импорт:
  - XLSX: колонки `Фамилия | Имя | Отчество | СНИЛС | Должность | ИНН Заказчика | Наименование ЮЛ Заказчика | ИНН УЦ | Наименование УЦ | Результат | № программы | Дата | № протокола`
  - XML: парсинг RegistrySet по XSD-схеме (lxml)
  - Валидация: СНИЛС (11 цифр), программа (1–29, кроме 5), результат (Удовлетворительно / Неудовлетворительно), дата (не в будущем)
  - Поддержка нескольких программ через запятую в одной ячейке (создаётся несколько записей)
  - Если данные уже загружены — диалог: объединить (пропуская дубли по СНИЛС+программа), удалить старые или отменить загрузку (модальный QDialog с тремя кнопками: `#dialogPrimaryBtn`, `#toolbarDangerBtn`, `#dialogDangerBtn`)
- Кнопка «Создать шаблон» — генерирует .xlsx с заголовками для заполнения (openpyxl)
- Экспорт отчёта об ошибках импорта в .xlsx
- Сигнал `data_loaded.emit(records, merge_mode)` — передаёт данные на вкладку «Просмотр данных»

**2.1.3. Ввод данных работника (ручной)**
- Поля: Фамилия, Имя, Отчество, СНИЛС (11 цифр, автоформатирование в вид `123-456-789 00`), Должность, Номер программы (1–29, несколько через запятую), Номер протокола, Результат (выпадающий список: Удовлетворительно / Неудовлетворительно), Дата (ДД.ММ.ГГГГ)
- Кнопка «Справка» — показывает перечень программ (двойной клик вставляет номер)
- Кнопка «Сохранить данные» — добавляет запись
- Валидация: обязательные поля, формат СНИЛС, корректность программы, дата не в будущем

1. **Тулбар** — `QHBoxLayout`:
   - Слева: `QLineEdit` `search_edit` (placeholder «🔍 Поиск...»)

2. **Таблица** — `QTableWidget` `table`:
   - 13 колонок (ФИО, СНИЛС, Должность, ИНН/Название заказчика, ИНН/Название УЦ, Результат, № программы, Дата, № протокола, скрытое поле id)
   - Многострочные заголовки
   - AlternatingRowColors, SelectRows, NoEditTriggers, сортировка включена
   - Контекстное меню на таблице и заголовке: «Редактировать» (диалог), «Удалить» (подтверждение)

3. **Статусная строка** — `QLabel` `status_label` («Записей: 0 | Выбрано: 0»)

  - Диалог сохранения .xml

**Персистентность:**

- Автозагрузка при старте приложения

### 2.3. Вкладка «Передача данных»

**Назначение:** Отправка XML в Минтруд, запрос регистрационных номеров, поиск по СНИЛС.

**Макет вкладки:** `QVBoxLayout` + `QScrollArea`, внутри шесть `QGroupBox`, расположенных вертикально. В базовом классе (`BaseDataTransferTab`) используется упрощённая версия. Наследник (`DataTransferTab`) добавляет цвета, статус-индикаторы и прогресс-бар. Стилизация QGroupBox через глобальный QSS: `font-weight: bold; border-radius: 5px; margin-top: 10px`.

1. **Группа «API ключ»** — `QLineEdit` `api_key_input` (Password echo, max 32 символа) + кнопка «Показать» (checkable) + кнопка «Вставить» + кнопка «Сохранить ключ» (синяя). В `DataTransferTab` дополнительно: QLabel `conn_status_dot` (12×12, `border-radius: 6px`, серый/зелёный/красный) + `conn_status_text` + кнопка «Проверить подключение» (зелёная `#27AE60`).

2. **Группа «Настройки прокси»** — три `QRadioButton` (`proxy_off_rb` / `proxy_auto_rb` / `proxy_manual_rb`) в `QButtonGroup`, обёрнутые в QFrame (стилизованная панель с border-radius). При выборе «Вручную» показываются `QLineEdit` (URL, логин, пароль). Чекбокс «Проверять TLS». `QComboBox` выбора transport backend (Auto / Requests / WinINET). Кнопки: «Сохранить» (синяя), «Проверить» (синяя).

3. **Группа «Электронная подпись (.sig)»** — `QLineEdit` `sig_file_input` (read-only, placeholder «Файл .sig не выбран (только для отправки в РОЛ)`) + кнопка «Выбрать». Выбор файла электронной подписи `.sig` для отправки XML в РОЛ.

4. **Группа «Отправка XML»** — `QLineEdit` `xml_file_input` (read-only) + кнопка «Выбрать XML». Большая зелёная кнопка «Отправить XML на сервер» (44px min height, 14px font, `bg=#27AE60`). Большая красная кнопка «Отправить XML и ПОДПИСАТЬ» (44px min height, 14px font, `bg=#E74C3C`) — отправляет XML с подписью `.sig`, флаг `<NeedSend>true</NeedSend>`, с подтверждением перед отправкой. `QProgressBar` `send_progress` (indeterminate, 6px высота). `QLineEdit` `last_setid_display` (read-only) для отображения последнего SetId.

5. **Группа «Запрос по SetId»** — `QLineEdit` `query_setid_input` (300px) + кнопка «Запросить номера».

6. **Группа «Запрос по СНИЛС»** — `QLineEdit` `query_snils_input` (300px) + кнопка «Найти».

**setObjectName:** не используются; все стили — через inline QSS или `_btn_style()` helper.

**2.3.1. API ключ**
- Поле ввода API-ключа (32 символа, из кабинета edu.rosmintrud.ru)
- Кнопка «Сохранить ключ» — шифрованное сохранение в `data/api_key.json`
- Валидация: длина 32 символа

**2.3.2. Настройки прокси**
- Режимы: «Без прокси», «Авто (системные)» (определение через реестр Windows), «Вручную»
- При ручном режиме: URL прокси, логин, пароль (шифруется, Fernet)
- Чекбокс «Проверять TLS» (для корпоративных прокси с SSL-инспекцией)
- Поддержка NTLM, Kerberos/Negotiate, Basic-аутентификации
- Сохранение настроек прокси в зашифрованном `data/proxy_settings.json`

**2.3.3. Выбор transport backend**
- Авто (пробует requests, затем WinINET) — режим по умолчанию
- Requests (библиотека requests, Windows Integrated Authentication)
- WinINET (Windows Internet API, лучшая поддержка корпоративных прокси)
- Автоматический fallback между транспортами при SSL-ошибках
- Retry-политика: 3 попытки с экспоненциальной задержкой (429, 500, 502, 503, 504)

**2.3.4. Диагностика сети**
- Кнопка «Диагностика сети» — проверка доступности `edu.rosmintrud.ru`
- Отображение статуса DNS, TCP-соединения, TLS-рукопожатия
- Определение типа прокси (системный / прямой / без прокси)
- Вывод результатов в информационное окно

**2.3.5. Отправка XML (без подписи)**
- Выбор XML-файла (кнопка «Выбрать XML»)
- Кнопка «Отправить XML на сервер» (зелёная) — формирует multipart-запрос (Request.xml с `<NeedSend>false</NeedSend>` + data.olot без `.sig`) и отправляет на `edu.rosmintrud.ru/api/set/push`
- При успехе: получение SetId, уведомление, отображение SetId в поле UI, автоматическая передача записей в «Журнал проверки знаний»
- При ошибке: отображение кода и сообщения об ошибке. Полный ответ сервера сохраняется в `log/error_response.txt` (UTF-8 BOM)

**2.3.6. Отправка XML с электронной подписью (в РОЛ)**
- Дополнительно к выбору XML требуется выбрать файл электронной подписи `.sig` в группе «Электронная подпись (.sig)»
- Кнопка «Отправить XML и ПОДПИСАТЬ» (красная, `bg=#E74C3C`, 44px min height, 14px bold) — перед отправкой запрашивает подтверждение пользователя
- Формирует multipart-запрос:
  - Request.xml с `<NeedSend>true</NeedSend>` (немедленная передача в РОЛ)
  - data.olot — ZIP-архив, содержащий Data.xml + файл `.sig`
- Отправляется на `edu.rosmintrud.ru/api/set/push`
- При успехе: получение XML-ответа с корневым элементом `<Response>`, содержащим:
  - `<SetId>` — номер созданного набора
  - `<SendEducatedPerson>` — true (успешно отправлено в РОЛ) / false
  - `<Message>` — дополнительные комментарии
- SetId отображается в поле `last_setid_display` и передаётся в журнал
- При ошибке: отображение кода и сообщения об ошибке. Полный ответ сервера сохраняется в `log/error_response.txt` (UTF-8 BOM)
- **Статус:** функционал не тестировался по причине отсутствия файла `.sig` для тестирования

**2.3.7. Запрос по SetId**
- Поле ввода SetId
- Кнопка «Запросить номера» — пагинированный запрос к `edu.rosmintrud.ru/api/GetEducatedPersonXML`
- Результат: экспорт в XLSX с колонками `Номер записи в реестре | ФИО | СНИЛС | Должность | ИНН работодателя | Наименование работодателя | Номер программы | Название программы | Номер протокола | Дата | Зачёт`
- Автоматическое обновление baseNo в «Журнале проверки знаний» (статус меняется с «pending» на «received»)

**2.3.8. Запрос по СНИЛС**
- Поле ввода СНИЛС
- Кнопка «Найти» — запрос к API по СНИЛС
- Отображение найденных записей

### 2.4. Вкладка «Журнал проверки знаний»

**Назначение:** Хранение и просмотр истории отправок XML на сервер Минтруда, отслеживание регистрационных номеров.

**Макет вкладки:** `QVBoxLayout` (панель фильтров QFrame + тулбар QFrame + QTableWidget + статус QLabel).

1. **Панель фильтрации** (`QFrame`) — два ряда в `QVBoxLayout`:
   - Ряд 1: `QLineEdit` `search_input` (placeholder «Поиск: Фамилия, Имя или СНИЛС») + `QComboBox` `setid_combo` (фильтр по SetId) + `QComboBox` `status_combo` (статус: Все/pending/received)
   - Ряд 2: `QDateEdit` `date_from` / `date_to` (календарь, формат dd.MM.yyyy) + кнопка «Сбросить»

2. **Тулбар** (`QFrame`) — 6 кнопок в `QHBoxLayout`:
   - «Экспорт в XLSX», «Импорт из Excel», «Шаблон журнала», «Печать протоколов», «Обновить по SetId», «Удалить» (красная `#E74C3C`)

3. **Таблица** — `QTableWidget` `table`:
   - 15 колонок (14 видимых + 1 скрытая UUID). Колонки: Дата отправки, SetId, ФИО, СНИЛС, Должность, Программа, Дата экзамена, Протокол, Результат, Рег. номер, Статус и др.
   - AlternatingRowColors, SelectRows, NoEditTriggers
   - Цветовая индикация статуса: «pending» — оранжевый фон, «received» — зелёный фон
   - Контекстное меню: «Удалить»

4. **Статусная строка** — `QLabel`

**setObjectName:** не используются; стилизация через inline QSS (delete_btn красный).

**Модель данных (JournalRecord):**
- `uuid` — уникальный идентификатор записи
- `send_date` — дата/время отправки
- `set_id` — идентификатор набора от сервера
- `xml_file` — путь к отправленному XML
- `last_name, first_name, middle_name` — ФИО
- `snils` — СНИЛС (формат «123-456-789 00»)
- `position` — должность
- `program_id` — номер программы («1»–«29»)
- `program_title` — название программы
- `exam_date` — дата экзамена
- `protocol` — номер протокола
- `result` — результат
- `base_no` — регистрационный номер (заполняется после запроса по SetId)
- `status` — «pending» (ожидает) / «received» (получен)

**Функционал:**
- Панель фильтрации: поиск по ФИО/СНИЛС, фильтр по SetId, статусу, номеру протокола, диапазону дат
- Кнопка «Сбросить» — очищает все фильтры
- Кнопка «Экспорт в XLSX» — выгрузка отфильтрованных записей
- Кнопка «Удалить» — удаление выбранных записей (красная)
- Контекстное меню: «Удалить»
- Хранение: `data/app_data.db` (таблица `exam_journal`)
- Менеджер: `JournalManager` (CRUD, поиск, фильтрация, обновление baseNo по SetId)

**2.7.1. Определение статуса сотрудника (aggregate — по всем программам)**

Статус сотрудника в сводке определяется не по одной программе, а по совокупности всех его программ, где `need_training = 1`:

1. Если **хотя бы одна** программа имеет статус `not_trained` (нет даты обучения) → статус сотрудника **«Не обучен»**
2. Иначе, если **хотя бы одна** программа имеет статус `expired` → статус сотрудника **«Просрочено»**
3. Иначе (все программы `trained`) → статус сотрудника **«Обучен»**

Приоритет: `not_trained` > `expired` > `trained`.

Этот агрегированный статус используется в:
- Статистических карточках (считается количество **сотрудников**, а не программ)
- Цветовой индикации строки сотрудника в таблице
- Планировании обучения (одна строка на сотрудника)

**2.7.2. Текущая ситуация**

Кнопка «Текущая ситуация» — формирует мгновенный отчёт по статусам всех сотрудников на сегодняшнюю дату.

**Алгоритм:**
1. Перебор всех сотрудников из БД
2. Для каждого сотрудника — определение агрегированного статуса через `_get_employee_status()` с учётом настройки периода обучения (`_b_period_3years`)
3. Маппинг статуса:
   - `not_trained` → причина «Не обучен», приоритет «Высокий», срок 60 дней
   - `expired` → причина «Просрочено», приоритет «Высокий», срок 30 дней
   - `trained` → причина «Обучен», приоритет «Низкий», срок = `exam_date + period_years`
4. Сортировка: Высокий > Средний > Низкий, затем по фамилии

**Результат:** диалоговое окно с карточками статистики (всего, высокий, средний, низкий) и таблицей:
- №, ФИО, СНИЛС, Должность, Программа, Последняя дата обучения, Дата окончания, Основание, Приоритет

**Запрос данных из реестра Минтруда по СНИЛС:**
- Кнопка «Запросить из реестра» — для всех сотрудников (с паузой 0.5 сек между запросами)
- Контекстное меню → «Запросить из реестра» — для одного сотрудника
- Брать последнюю успешную запись по дате по каждому номеру программы
- Если последняя запись «Неудовлетворительно» — статус «Не обучен»
- Полученные данные содержат: ФИО, СНИЛС, должность, номера программ, даты обучения, протоколы, результат, рег. номера

**Импорт/экспорт XLSX:**
- Импорт: обязателен столбец СНИЛС; распознаются столбцы: Фамилия, Имя, Отчество, СНИЛС, Должность, а также столбцы вида «программа #N Потребность», «программа #N Дата обучения» и т.д.
- Экспорт: столбцы ФИО, СНИЛС, Должность, затем для каждой программы — Потребность, Дата обучения, Протокол, Рег.№
- Экспорт (все): выгрузка без фильтров; если таблица пуста — создаётся шаблон для заполнения

**2.7.3. Формирование планов обучения**

**Логика формирования (на уровне сотрудника, а не программы):**

Для каждого сотрудника определяется **агрегированный статус** через `_get_employee_status()`. В плане создаётся **одна строка на сотрудника** (не на программу). Причина и приоритет определяются по статусу сотрудника в целом.

**Алгоритм:**

1. Получить всех сотрудников из БД
2. Для каждого сотрудника:
   - Загрузить все программы (`employee_programs`)
   - Определить агрегированный статус через `_get_employee_status(emp_id, programs)`
   - Если статус `not_trained` и чекбокс «Включать не обученных» активен:
     - Причина: «Не обучен», приоритет: «Высокий», срок: сегодня + 60 дней
   - Иначе если статус `expired` и чекбокс «Включать просроченных» активен:
     - Причина: «Просрочено», приоритет: «Высокий», срок: сегодня + 30 дней
    - Иначе если статус `trained` и чекбокс «Включать истекающих» активен:
      - Если `expiry_date.year == plan_year` (expiry_date вычисляется с учётом периода для данной программы: 3 года для программ А и В (если чекбокс включён), 1 год для программ В (если чекбокс выключен)):
        - Причина: «Истекает срок действия», приоритет: «Средний», срок: expiry_date
3. Сортировка: Высокий > Средний > Низкий, затем по фамилии

**Параметры (диалог перед формированием):**
- ☑ Включать не обученных
- ☑ Включать просроченных
- ☑ Включать истекающих в планируемом году
- ☐ Включать неуспешно прошедших проверку знаний
- Кнопки: «Сформировать», «Отмена»

**Результат — диалог PlanDialog:**

Верхняя панель с карточками статистики (цветная индикация):
- Всего в плане (синий)
- Высокий приоритет (красный)
- Средний приоритет (жёлтый)
- Низкий приоритет (зелёный)

Таблица с колонками:
- №, ФИО, СНИЛС, Должность, Программа, Последняя дата обучения, Дата окончания действия, Основание, Приоритет

Приоритет в таблице выделяется цветом: Высокий (🔴), Средний (🟡), Низкий (🟢).

**Экспорт XLSX:**
- Лист 1: «План» — таблица плана со стилизованными заголовками
- Лист 2: «Сводка» — количество сотрудников по программам
- Имя файла: `План_обучения_{год}.xlsx`

**2.7.4. Отчёт по обученным за год**

Кнопка «Отчет по обученным» (зелёная, в строке отчётов) — формирует таблицу с группировкой по категориям программ:
- А (программа №3 — общие вопросы охраны труда)
- Б (программа №4 — безопасные методы)
- В (программы №6–29 — специальные)
- ОПП (программа №1 — первая помощь)
- СИЗ (программа №2 — СИЗ)

**Логика подсчёта:**
- Выбираются все записи employee_programs с `need_training = 1`
- Если дата обучения пуста (не обучен) → считается в «Подлежат обучению»
- Если дата обучения в текущем году → считается и в «Подлежат обучению», и в «Обучено»
- Если дата обучения ровно `period_years` назад (3 года для категорий А, Б, ОПП, СИЗ; 1 или 3 года для В в зависимости от чекбокса) → считается только в «Подлежат обучению» (истекает срок)
- Некорректные даты → считаются в «Подлежат обучению»

Результат: модальный диалог с таблицей (Программа | Подлежат обучению в текущем году | Обучено в текущем году). Заголовки колонок — в 2 строки (`\n` после «обучению»/«Обучено»).

- Хранение: до 5 последних копий в `%APPDATA%/Excel_to_XML/backups/`
- Именование: `app_data.db.backup.0` … `app_data.db.backup.4` (ротация)

**Восстановление:** ручное — копирование файла из папки `backups/` в `%APPDATA%/Excel_to_XML/app_data.db`.

### 2.13. Обработка ошибок

- `global_exception_handler` — перехват необработанных исключений
- Логирование в файлы в папке `log/`
- Фильтрация чувствительных данных в логах (SensitiveDataFilter: маскировка СНИЛС, паролей, API-ключей, ФИО, URL с credentials, прокси)

### 3.5. Шифрование и безопасность

**Принцип:** SQLite-БД — обычная (без файлового шифрования). Персональные данные защищены на уровне отдельных полей (ФИО, СНИЛС). Конфиденциальные настройки шифруются целиком.

| Данные | Метод | Файл |
|--------|-------|------|
| SQLite-БД (ФИО, СНИЛС, программы, журнал) | Полевое шифрование (Fernet) | `app_data.db` |
| API-ключ Минтруда | Fernet | `api_key.json` |
| Настройки УЦ и Заказчика | Fernet | `org_settings.json` |
| Данные комиссии | Fernet | `commission_data.json` |
| Пароль прокси | Fernet | `proxy_settings.json` |
| Мастер-ключ | DPAPI (CryptProtectData) / raw fallback | `master.key` |

**Ключ шифрования (Мастер-ключ):**
- **Основной режим:** мастер-ключ генерируется случайно (32 байта) и защищается Windows DPAPI (привязка к учётной записи + машине)
- **Fallback:** если DPAPI недоступен, мастер-ключ сохраняется в открытом виде с предупреждением в логе

**Жизненный цикл БД:**
1. **Запуск**: SQLite открывается напрямую (WAL-журналирование)
2. **Работа**: чтение/запись зашифрованных полей через Fernet-ключ
3. **Поиск по СНИЛС**: через хеш-поле `snils_hash` (SHA256) — сам СНИЛС остаётся зашифрованным
4. **Бэкап**: копия `app_data.db` через shutil.copy2 — данные уже зашифрованы
5. **Закрытие**: обычное закрытие SQLite-соединения (повторного шифрования не требуется)

**Логирование:**
Все логи фильтруются через `SensitiveDataFilter`:
- СНИЛС: маскируются (`123-456-789 00` → `***-***-*** **`)
- Пароли: заменяются на `***`
- API-ключи: заменяются на `***`
- URL с credentials: заменяются на `https://***:***@***`

## 6. Интеграция с API Минтруда

**Эндпоинты:**
- `POST https://edu.rosmintrud.ru/api/set/push` — отправка XML
- `POST https://edu.rosmintrud.ru/api/GetEducatedPersonXML` — запрос данных по SetId или СНИЛС

**Формат запроса (GetEducatedPersonXML):**
```xml
<EducatedPersonFilter>
    <ApiKey>32-символьный-ключ</ApiKey>
    <PageNo>1</PageNo>
    <PageSize>5000</PageSize>
    <Snils>XXX-XXX-XXX XX</Snils>
    <!-- или -->
    <SetId>идентификатор-набора</SetId>
</EducatedPersonFilter>
```

**Особенности запроса:**
- СНИЛС передаётся в формате `XXX-XXX-XXX XX` (с дефисами и пробелом)
- Элемент `<ApiKey>` обязателен во всех запросах — без него сервер возвращает ошибку авторизации
- XML-запрос не содержит пространства имён на корневом элементе `EducatedPersonFilter`
- Пагинация: переход к следующей странице пока `len(records) == page_size` (5000); break при меньшем количестве
- ISO-даты в ответе (`2025-09-26T00:00:00`) нормализуются в формат `DD.MM.YYYY` через `_normalize_api_date()`

**Формат ответа:**
- `EducatedPersons` — список `RegistryRecord`, каждый содержит:
  - `Worker` (Snils, LastName, FirstName, MiddleName, Position, EmployerInn, EmployerTitle)
  - `Test` (learnProgramId, LearnProgramTitle, ProtocolNumber, Date, isPassed)
  - `baseNo` — регистрационный номер в реестре

**Обработка ошибок:**
- При ошибке отправки XML полный ответ сервера сохраняется в `log/error_response.txt` (UTF-8 BOM)
- Формат сохранения: статус-код + заголовки + тело ответа (в сыром виде)
- Файл перезаписывается при каждой новой ошибке
